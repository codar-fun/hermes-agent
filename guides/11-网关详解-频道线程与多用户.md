# 11 · 网关详解：频道 / 线程上下文、回复与多用户

这是 [05 · 消息网关与平台连接](./05-消息网关与平台连接.md) 的进阶补充，深入讲清三件容易踩坑的事：

1. 网关到底做了哪些事；
2. 在 Discord / Slack / Telegram 里，**channel（频道）与 thread（线程/话题）如何映射到不同的会话上下文**；
3. **回复对象（reply）与 @mention 如何配置**，以及**在多用户聊天室里上下文怎么走**。

> 本文所有键名、默认值、会话键格式均核对自源码（`gateway/session.py`、`gateway/config.py`、各平台适配器）。

---

## 1. 网关功能全面介绍

消息网关（`hermes gateway`）是一个常驻进程，把外部聊天平台和内部的 `AIAgent` 串起来。它负责：

| 职责 | 实现 |
|------|------|
| **多平台接入** | 一个进程同时跑 31 个平台适配器（`gateway/platforms/`），各自负责收消息、发消息、媒体、按钮、表情 |
| **消息 → 会话路由** | 根据来源把每条消息映射到一个会话键（session key），决定它落到哪个 `AIAgent` 上下文（见第 3 节）|
| **智能体缓存** | LRU 缓存最多 128 个活跃 `AIAgent`，空闲 1 小时（`_AGENT_CACHE_IDLE_TTL_SECS=3600`）后回收 |
| **访问控制** | 白名单 / DM 配对码 / 群内是否要求 @（见 [05](./05-消息网关与平台连接.md) 与第 5 节）|
| **流式渐进编辑** | 把同步智能体的输出桥接为平台上的渐进消息编辑（`gateway/stream_consumer.py`）|
| **会话重置** | 按空闲 / 每日策略自动开新会话（`session_reset`，见第 6 节）|
| **投递与通知** | 定时任务结果、主动消息投递到 Home 频道（`gateway/delivery.py`）|
| **生命周期钩子** | `~/.hermes/hooks/` 下的事件钩子（startup / session / agent / command）|
| **运行管理** | 作为 systemd / launchd 服务运行，支持 `start/stop/restart/status/logs/install` |

```bash
hermes gateway setup       # 配置平台
hermes gateway start       # 后台启动
hermes gateway status      # 状态 + PID
hermes gateway restart     # 排空活跃任务后优雅重启
hermes gateway logs        # 看日志
```

## 2. 平台连接配置（响应判定相关）

[05](./05-消息网关与平台连接.md) 已列出各平台的**连接凭据**（Token / AppID 等）。这里补上**「何时响应」**这一类配置——它们决定 bot 在群里到底说不说话。几乎所有平台都遵循同一套命名约定（已核对存在）：

| 约定键（前缀为平台名） | 作用 |
|------|------|
| `<平台>_REQUIRE_MENTION` | 群里是否必须 @bot / 回复 bot 才响应 |
| `<平台>_FREE_RESPONSE_CHANNELS` / `_CHATS` / `_ROOMS` | 这些频道里无需 @，bot 对所有消息都回（优先级高于 require_mention）|
| `<平台>_THREAD_REQUIRE_MENTION` | 线程内是否仍要求 @（Discord/Matrix）|
| `<平台>_STRICT_MENTION` | 线程内每条都要求 @（Slack）|
| `<平台>_MENTION_PATTERNS` | 自定义唤醒词正则（无需 @ 也能触发）|
| `<平台>_ALLOWED_CHANNELS` / `_CHATS` | 频道白名单（只在这些频道响应）|
| `<平台>_IGNORED_CHANNELS` / `_IGNORED_THREADS` | 频道/线程黑名单 |
| `<平台>_ALLOW_BOTS` | 是否接收其他 bot 的消息（`none`/`mentions`/`all`）|
| `<平台>_ALLOWED_USERS` | 用户白名单 |
| `<平台>_HOME_CHANNEL` | 定时任务/通知投递目的地 |

确认存在该类键的平台包括：Discord、Slack、Telegram、Matrix、Mattermost、飞书、钉钉、Signal、WhatsApp、BlueBubbles 等。第 5 节给出三大平台的完整取值与默认值。

## 3. 核心：消息如何映射到会话（session key）

**这是理解「频道/线程/多用户上下文」的关键。** 网关用 `build_session_key()`（`gateway/session.py`）从每条消息的来源 `SessionSource` 确定性地算出一个会话键，相同的键 = 同一个 `AIAgent` 上下文（同一段对话历史）。

参与计算的字段：`platform`、`chat_type`（`dm`/`group`/`channel`/`thread`）、`chat_id`、`thread_id`、`user_id`，外加两个开关：

- `group_sessions_per_user`（**默认 `True`**）—— 普通群/频道里，**每个用户各自一个独立会话**。
- `thread_sessions_per_user`（**默认 `False`**）—— 线程内，**所有人共享同一个会话**。

会话键的真实格式（核对自源码）：

```
私聊（DM）：
  agent:main:{platform}:dm:{chat_id}
  agent:main:{platform}:dm:{chat_id}:{thread_id}     # DM 内有话题时

群/频道：
  agent:main:{platform}:{chat_type}:{chat_id}[:{thread_id}][:{user_id}]
                                              ↑线程时加      ↑仅在「按用户隔离」时加
```

### 默认行为一览

| 场景 | 是否共享上下文 | 会话键是否含 user_id |
|------|----------------|----------------------|
| **私聊 DM** | 永远按用户隔离（每个 DM 独立）| —（DM 本身就是单人）|
| **普通群/频道**（无线程）| ❌ 每个用户**各自独立**会话 | ✅ 含 user_id |
| **线程 / 话题内**（Discord thread、Slack thread_ts、Telegram 论坛话题）| ✅ 同一线程内**所有人共享**一个会话 | ❌ 不含 user_id |

直观理解：

- Discord 一个频道里 5 个人各自 @bot → **5 个互相隔离的会话**（各聊各的，互不串）。
- Discord 一个**线程**里 5 个人 → **1 个共享会话**（bot 看到的是一段多人对话）。
- Slack thread、Telegram 论坛话题同理：**线程 = 共享上下文**。

### 想改默认？

在 `config.yaml` 顶层设这两个网关键即可：

```yaml
# 让普通群也变成「全群共享一个上下文」（而非每人一份）
group_sessions_per_user: false

# 让线程也按用户隔离（每人在同一线程里有各自上下文）
thread_sessions_per_user: true
```

## 4. channel vs thread：三平台怎么区分

`thread_id` 取自各平台的「线程」概念，一旦存在就会进入会话键 → 自动开出独立的线程会话：

| 平台 | channel（频道）| thread（线程/话题）= `thread_id` 来源 |
|------|----------------|----------------------------------------|
| **Discord** | 文字频道 `channel_id` | Discord 线程（thread 的 channel_id）|
| **Slack** | 频道 `C...` | 线程时间戳 `thread_ts` |
| **Telegram** | 群 `chat_id`（负数）| 论坛话题 `message_thread_id`；或 DM 话题（见下）|

**含义**：当对话从频道进入某个线程，会话键变了 → 那是**一段全新的、与频道主对话隔离**的上下文（线程内多人共享）。回到频道主层 → 回到原来的频道会话。

### Discord：自动开线程

Discord 适配器默认会为频道里的非线程消息**自动开一个线程**来回复，让每个话题各自成线程：

```bash
DISCORD_AUTO_THREAD=true            # 默认 true：自动开线程回复
DISCORD_NO_THREAD_CHANNELS=...      # 这些频道不自动开线程（如公告频道）
DISCORD_THREAD_REQUIRE_MENTION=false # 默认 false：线程里参与过后无需再 @
```

### Telegram：两种「话题」

- **论坛话题（forum topics）**：超级群里的官方话题，按 `message_thread_id` 各自独立会话。可用 `TELEGRAM_ALLOWED_TOPICS` 白名单限定只在某些话题响应。
- **DM 话题（`/topic` 命令）**：让**同一个私聊**里并行多条独立会话线。在 `config.yaml` 配置（需 Bot API 9.4+）：

  ```yaml
  telegram:
    dm_topics:
      - chat_id: 123456789          # 你的 Telegram 用户 ID
        topics:
          - name: "工作"
            thread_id: 100          # 首次运行后自动回填
          - name: "生活"
            skill: "note-taking"    # 可选：该话题路由到某技能
  ```

  会话内用 `/topic`：

  ```text
  /topic              # 查看状态 / 启用
  /topic off          # 关闭话题模式
  /topic <session_id> # 在新话题里恢复某个历史会话
  ```

  每个话题都有独立 `thread_id` → 独立的对话历史与上下文。

## 5. 回复对象（reply）与 @mention 配置

下面是 Discord / Slack / Telegram 三大平台的完整取值（已核对键名与默认值）。

> 通则：**私聊（DM）永远不受 require_mention 限制**，直接响应。下列 mention 规则只作用于群/频道。

### Discord

| 键 | 默认 | 取值 / 行为 |
|----|------|-------------|
| `DISCORD_REQUIRE_MENTION` | `true` | 群里需 @bot 才响应；`false` = 回所有消息 |
| `DISCORD_THREAD_REQUIRE_MENTION` | `false` | `false`：在线程里参与过后无需再 @；`true`：线程内每条都要 @（多 bot 防互触发）|
| `DISCORD_FREE_RESPONSE_CHANNELS` | 空 | 这些频道无需 @；`*` = 所有频道。优先级高于 require_mention |
| `DISCORD_REPLY_TO_MODE` | `first` | **回复对象模式**：`off`=普通消息不引用；`first`=多段回复仅第一段引用触发消息；`all`=每段都引用 |
| `DISCORD_ALLOWED_CHANNELS` | 空 | 频道白名单（设了就只在这些频道响应）|
| `DISCORD_IGNORED_CHANNELS` | 空 | 频道黑名单 |
| `DISCORD_ALLOWED_ROLES` | 空 | 触发 bot 需具备的角色（仅服务器内）|
| `DISCORD_AUTO_THREAD` / `DISCORD_NO_THREAD_CHANNELS` | `true` / 空 | 自动开线程回复 / 例外频道 |
| `DISCORD_ALLOW_BOTS` | `none` | `none`/`mentions`/`all`：是否接收其他 bot 消息 |
| `DISCORD_REACTIONS` | `true` | 处理中/完成时加 👀✅❌ 等表情 |

**响应判定**（满足其一即回）：是 DM｜在 free-response 频道｜`require_mention=false`｜被 @｜在线程里且此前参与过（`thread_require_mention=false`）｜回复的是 bot 消息。

### Slack

| 键 | 默认 | 取值 / 行为 |
|----|------|-------------|
| `SLACK_REQUIRE_MENTION` | `true` | 频道里需 @bot 才响应；`false` = 听全部 |
| `SLACK_STRICT_MENTION` | `false` | `false`：被 @ 一次后，该线程后续消息都响应；`true`：每条都要 @（含线程）|
| `SLACK_FREE_RESPONSE_CHANNELS` | 空 | 这些频道无需 @；`*` = 所有频道 |
| `SLACK_ALLOWED_CHANNELS` | 空 | 频道白名单 |
| `SLACK_ALLOWED_USERS` | 空 | 用户白名单；`*` = 所有人 |
| `SLACK_ALLOW_BOTS` | `none` | 同 Discord |
| `SLACK_REACTIONS` | `true` | 表情反馈 |

**回复对象**：Slack **默认在线程内回复**（带 `thread_ts`）。bot 会记住「自己被 @ 过的线程」和「自己发过消息的线程」，在这些线程里自动跟进（除非 `SLACK_STRICT_MENTION=true`）。

### Telegram

| 键 | 默认 | 取值 / 行为 |
|----|------|-------------|
| `TELEGRAM_REQUIRE_MENTION` | `false` | 群里是否需 @bot / 回复 bot 才响应 |
| `TELEGRAM_FREE_RESPONSE_CHATS` | 空 | 这些群无条件响应 |
| `TELEGRAM_ALLOWED_CHATS` | 空 | 群白名单（设了就只在这些群响应）|
| `TELEGRAM_GUEST_MODE` | `false` | `true`：非白名单群仅能通过显式 @ 触发 |
| `TELEGRAM_MENTION_PATTERNS` | 空 | 自定义唤醒词正则（JSON 数组或换行分隔），无需 @ 也触发 |
| `TELEGRAM_EXCLUSIVE_BOT_MENTIONS` | `true` | 消息 @ 了别的 bot 时，本 bot 除非被点名否则不响应 |
| `TELEGRAM_ALLOWED_TOPICS` | 空 | 论坛话题白名单 |
| `TELEGRAM_OBSERVE_UNMENTIONED_GROUP_MESSAGES` | `false` | `true` + require_mention：把未 @ 的群聊也存进上下文，但只在被 @ 时才回复（让 bot「听得到」群里在聊什么）|

**mention 检测**：识别 `@botusername`、回复 bot 的消息、`/cmd@botname`，以及 `TELEGRAM_MENTION_PATTERNS` 自定义正则。
**回复对象**：默认以 Telegram「回复」形式指向触发它的那条用户消息（`reply_to_mode: first`）。

## 6. 多用户聊天室：上下文怎么走

这是最容易困惑的点。结论先行：

> **在「共享会话」里**（即线程，或把 `group_sessions_per_user` 设成 `false` 的群），多个用户的消息进入**同一段上下文**；每条消息会被自动加上**发送者前缀**，让模型分得清谁在说话。

### 发送者归属（attribution）

当判定为共享多用户会话（`is_shared_multi_user_session()`）时，网关在消息前注入发送者名字（`gateway/run.py`）：

```python
if _is_shared_multi_user and source.user_name:
    message_text = f"[{source.user_name}] {message_text}"
```

模型看到的就是：

```
[Alice] 帮我看下这个设计稿
[Bob] 我也想加个需求……
```

同时系统提示里会标注这是多用户会话（`gateway/session.py`）：

> **Session type:** Multi-user thread — messages are prefixed with [sender name]. Multiple users may participate.

所以模型知道：这是多人对话、每条带 `[发送者]`、可能有多人参与。

### 三种典型布局

| 布局 | 上下文行为 |
|------|------------|
| **普通群，默认**（`group_sessions_per_user=true`）| 每个用户**各自独立**会话；bot 只看到「我和这一个人」的对话，看不到别人。互不干扰，隐私性最好。|
| **群里 `group_sessions_per_user=false`** | 全群**共享一个**会话；所有人的消息（带 `[发送者]`）进同一上下文，bot 能综合群里多人的发言。|
| **线程 / 话题（默认）** | 线程内**所有人共享**一个会话（带 `[发送者]`）；这是线程的自然 UX。想每人隔离则设 `thread_sessions_per_user=true`。|

### 让 bot「旁听」群聊（Telegram）

如果希望 bot 平时不插话、但**被 @ 时能结合群里上下文**回答：

```yaml
telegram:
  require_mention: true
  observe_unmentioned_group_messages: true   # 未 @ 的消息也存进上下文，仅在被 @ 时回复
```

### 身份与隐私（PII）

- **PII-safe 平台**（WhatsApp、Signal、Telegram、BlueBubbles）：当开启 PII 脱敏时，系统提示里的用户/聊天标识会**哈希化**（如 `user_a1b2c3...`）。
- **Discord 例外**：因为 `discord` / `discord_admin` 工具需要真实的 `<@user_id>`、频道/服务器 ID，所以当加载了 Discord 工具时，系统提示里会以代码块形式给出真实 ID。
- 哈希仅作用于**展示层**（系统提示/会话描述）；底层消息路由始终用真实 ID。

## 7. 会话重置与上下文回收

两套机制会让上下文「重新开始」或从内存释放（互相独立）：

| 机制 | 配置 / 常量 | 行为 |
|------|-------------|------|
| **会话重置策略** | `session_reset.mode`（`both`/`idle`/`daily`/`none`）、`idle_minutes`（默认 1440=24h）、`at_hour`（默认 4 点）| 到期后开**新 session_id**，旧记录留在 `state.db`，新会话从空白开始 |
| **智能体缓存回收** | LRU 上限 128、空闲 TTL 3600 秒 | 仅从内存释放 `AIAgent`（关客户端、丢工具 schema）；下条消息到来时按会话键重建，**历史仍在 DB** |

```yaml
session_reset:
  mode: "both"        # idle + daily 都触发
  idle_minutes: 1440  # 空闲 24h 后重置
  at_hour: 4          # 每天凌晨 4 点重置
  notify: true        # 重置时通知用户
```

> 区别：**缓存回收**只是省内存，历史不丢、上下文延续；**会话重置**才是真正「翻篇」开新会话。

## 8. 常见诉求 → 推荐配置

| 你想要的效果 | 推荐配置 |
|--------------|----------|
| 群里安静，只在被 @ 时回复 | `<平台>_REQUIRE_MENTION=true`（Telegram 默认要手动开）|
| 群里像群成员一样自由参与 | `<平台>_REQUIRE_MENTION=false` 或把该群加入 `FREE_RESPONSE_CHATS/CHANNELS` |
| 群里每个人各聊各的、互不可见 | 保持默认 `group_sessions_per_user=true`（默认就是）|
| 让 bot 综合全群多人对话 | `group_sessions_per_user=false` |
| 线程里每人独立上下文 | `thread_sessions_per_user=true`（默认是共享）|
| bot 旁听群聊、被 @ 才答但带上下文 | Telegram：`require_mention=true` + `observe_unmentioned_group_messages=true` |
| 只在某几个频道工作 | `<平台>_ALLOWED_CHANNELS`/`_CHATS` 白名单 |
| 回复时引用用户原消息 | Discord：`DISCORD_REPLY_TO_MODE=first`（默认）；Telegram：默认即引用 |
| 一个私聊里开多条独立话题 | Telegram `/topic` + `telegram.dm_topics` 配置 |
